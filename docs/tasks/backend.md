# 后端任务

负责人：组长。先读 [docs/contract/](../contract/README.md)，接口的每个细节以它为准。

骨架里已经有的东西：

- `common/`：统一响应 `Result`、业务异常 `BizException`、全局异常处理。业务代码里出错就抛 `BizException`，不用自己拼错误响应。
- `health/`：健康检查接口，可以当作写控制器的样板。
- `meta/`、`schema/`、`data/`、`svc/`、`ai/`：五个空包，各自的职责写在 `package-info.java` 里。

每个任务的写法相同：先定“要记录的思考”里的决策，再按步骤做，最后逐条过验收标准。验收里的请求可以用 IDEA 的 HTTP Client、Postman 或 PowerShell 发。导入示例元模型的命令（在仓库根目录执行）：

```powershell
Invoke-RestMethod -Method Post -Uri http://localhost:8200/api/meta/import -ContentType 'application/json; charset=utf-8' -InFile docs/contract/samples/mes.json
```

两个已知的坑：

- Spring Boot 4 默认用 Jackson 3，`ObjectMapper` 要从 `tools.jackson.databind` 导入，不是 `com.fasterxml`。
- 测试用的内存数据库 H2 只适合不涉及建表改表的测试。建表、改表的 SQL 是 MySQL 专有的，用真实接口验收。

## B1 元模型的存取

**目标：** 能通过 `/api/meta` 保存和读取模块、模型的定义，能导入 `samples/mes.json`。这一步还不建业务表。预计 2.5 小时。

**要记录的思考**

- 决策 001：元模型的定义本身怎么存。
  - 方案 A：拆成多张表，模型、字段、服务、视图各一张。
  - 方案 B：模块一张表，模型一张表，每个模型的完整定义存成一个 JSON 文本列。
  - 比较这几点：保存一个模型要写多少条 SQL；导入导出和 AI 生成是否顺手；能不能用 SQL 按字段查；两个人同时改一个模型会怎样。
  - 我的建议是 B：契约里一个模型就是一份完整的文档，设计器、导入导出、AI 助手都是整份读写。代价是不能用 SQL 查“哪些模型有某种字段”，目前没有这个需求。你可以不同意，把理由写下来。
  - 试做：两种方案各写出建表语句，各数一下“保存一个 8 个字段的模型”要执行几条 SQL。
- 决策 012：数据访问为什么用 `JdbcTemplate`，不用上个项目的 MyBatis-Flex。提示：业务模型是运行时定义的，编译时没有对应的实体类。

**步骤**

1. 建元模型表。在 `src/main/resources/` 下新建 `schema.sql`，用 `CREATE TABLE IF NOT EXISTS`；在 `application.yml` 里加 `spring.sql.init.mode: always`，让它每次启动时执行。按方案 B 的话是两张表：
   - `meta_module`：`name` 主键、`display_name`、`icon`、`sort`。
   - `meta_model`：`name` 主键、`module_name`、`definition`（`MEDIUMTEXT`，存模型定义的 JSON）、`created_at`、`updated_at`。
2. 在 `meta/model/` 下用 Java `record` 定义 `ModuleDef`、`ModelDef`、`FieldDef`、`RelationDef`、`ServiceDef`、`ViewsDef` 等，键名和 [meta-model.md](../contract/meta-model.md) 完全一致。
3. 写 `MetaValidator`，每条规则对应一句明确的中文提示：
   - 标识不合规则；字段重名；字段名用了系统字段名。
   - `enum` 没有选项；关联字段没有 `relation`；`manyToOne` 指向的模型不存在；`oneToMany` 的 `mappedBy` 在子模型里找不到对应的 `manyToOne` 字段。
   - 视图里引用了不存在的字段；`form.tabs` 引用的不是 `oneToMany` 字段。
   - 修改模型时改了已有字段的类型。
   - 注意导入：一个包里的模型可以互相引用，校验“指向的模型是否存在”时要把同一个包里的模型算进去。
4. 写 `MetaDefaults`：补齐默认值，按契约里的规则生成默认视图。
5. 写 `MetaRepository`（用 `JdbcTemplate` 读写两张表）和 `MetaRegistry`（内存里的注册表：启动时全量加载，保存后更新，所有读取都走它）。
6. 写 `MetaService` 和 `MetaController`，实现契约里“元模型接口”一节的全部接口，包括 `menus`、`import`、`export`。
7. 给 `MetaValidator` 和默认视图写单元测试。

**验收标准**

- [ ] 导入 `mes.json`，返回 `{ "modules": 2, "models": 4 }`。
- [ ] `GET /api/meta/models/material` 返回 8 个字段，`views` 完整，`tableName` 有值。
- [ ] `GET /api/meta/menus` 返回“生产管理”（物料、产品）和“基础设置”（编码规则），顺序正确，`product_bom` 不出现。
- [ ] 新建一个不带 `views` 的模型，返回的定义里有按规则生成的默认视图。
- [ ] 模型名传 `Bad Name` 返回 400 和中文提示；重复新建返回 409；枚举字段没有选项返回 400；关联指向不存在的模型返回 400。
- [ ] 重启后端后，定义还在。
- [ ] `.\mvnw.cmd test` 通过，`MetaValidator` 至少有 6 条测试。

## B2 表结构同步

**目标：** 保存模型时，数据库里出现或更新对应的真实表。预计 2 小时。

**要记录的思考**

- 决策 002：业务数据怎么存。
  - 方案 A：每个模型建一张真实的表。
  - 方案 B：EAV，一张“记录-字段-值”大表。
  - 方案 C：一张通用表，记录整体存成 JSON 列。
  - 比较这几点：唯一约束和索引谁来保证；查询和排序好不好写；模型变更的代价；数据直不直观；IIDP 是怎么做的。
- 决策 005：模型改了以后，已有的表怎么办。至少回答：
  - 加字段时，老数据在新列上是什么值？
  - 删字段时，列和数据删不删？
  - `required` 用数据库的 `NOT NULL` 保证，还是只在应用层校验？提示：如果建成 `NOT NULL`，这个字段以后被“删除但保留列”时，新记录还插得进去吗？
  - `unique` 为什么应该交给数据库的唯一索引，而不是应用层先查再插？
  - MySQL 的建表改表语句不能回滚。“保存定义”和“改表”哪个先做，中途失败了怎么办？

**步骤**

1. 字段类型策略。定义接口 `FieldTypeHandler`，每种字段类型一个实现，负责三件事：这一列的建表片段、把请求里的 JSON 值转成数据库值、把数据库值转成响应里的 JSON 值。用一个注册表按类型名查找。以后加字段类型只需要加一个实现类。建议的列类型：

   | 字段类型 | 列类型 |
   |---|---|
   | `string` | `VARCHAR(length)` |
   | `text` | `TEXT` |
   | `integer` | `BIGINT` |
   | `decimal` | `DECIMAL(precision, scale)` |
   | `boolean` | `TINYINT(1)` |
   | `date` | `DATE` |
   | `datetime` | `DATETIME` |
   | `enum` | `VARCHAR(64)` |
   | `manyToOne` | `BIGINT` |
   | `oneToMany` | 不占列 |

2. `SchemaSync.create(model)`：拼建表语句。表名加统一前缀（例如 `md_`），避免和元模型表、SQL 关键字冲突。固定三列 `id`（自增主键）、`created_at`、`updated_at`，然后每个字段一列，`unique` 的字段加唯一索引，索引名要能反查出字段（例如 `uk_表名_列名`，B3 要用）。
3. `SchemaSync.alter(oldModel, newModel)`：比较新旧定义。新增字段加列；删除的字段按决策 005 的结论处理；`unique` 有变化就加或删索引。已有数据有重复导致唯一索引加不上时，返回 409 和能看懂的提示。
4. 所有表名、列名一律用反引号包起来，而且只能来自校验过的元模型，绝不直接用请求里的字符串。
5. 接进 `MetaService`：新建模型时建表，修改时改表。删除模型时，表是直接删还是改名保留，写进决策 005。
6. 不建数据库外键，引用完整性在 B4 里由应用层保证。想一想为什么，记进决策 009。

**验收标准**

- [ ] 导入 `mes.json` 后，在 MySQL 里执行 `SHOW TABLES`，能看到四张业务表。
- [ ] `SHOW CREATE TABLE` 物料表：列和类型符合上面的表，`code` 上有唯一索引。
- [ ] 给物料模型加一个字段 `brand` 后提交修改，表里多了一列，原有数据没丢。
- [ ] 再把 `brand` 去掉后提交，`GET` 模型定义里没有它了，表的处理和决策 005 里写的一致。
- [ ] 修改 `name` 字段的 `type`，返回 400。
- [ ] 以上全程不重启后端。
- [ ] 每种字段类型的建表片段各有一条单元测试。

## B3 通用数据接口

**目标：** `/api/data/{model}` 的查询、详情、新建、修改、删除对任意模型可用。预计 3 小时。

**要记录的思考**

- 决策 003：“动态生成 api”怎么实现。
  - 方案 A：一个通用控制器，模型名是路径变量。
  - 方案 B：每新建一个模型，就在运行时往 Spring 的 `RequestMappingHandlerMapping` 里注册一组新的映射。
  - 比较这几点：实现复杂度；模型删除后映射怎么清理；接口文档怎么生成；老师说的“动态生成”到底指什么。
- 决策 004：表名和列名是拼进 SQL 的，怎么保证不被注入。把你的规则写成三四句话，并且写清楚每一句防的是哪种攻击。

**步骤**

1. `DataController`：`@RequestMapping("/api/data/{model}")`，五个接口加 `options`（`options` 的实现放在 B4）。
2. `SqlBuilder`：输入模型定义和请求，输出 SQL 字符串和参数表。规则：
   - 表名、列名只从模型定义里取；请求里的字段名只用来在定义里查找，查不到就返回 400。
   - 所有值都走命名参数（`NamedParameterJdbcTemplate`）。
   - 比较运算符和排序方向用 `switch` 映射成固定的几种写法，不认识的返回 400。
3. 查询：`filters` 拼成 `WHERE`。`like` 要转义值里的 `%` 和 `_`；`in` 展开成多个参数；分页用 `LIMIT` 和 `OFFSET`；总数另发一条 `COUNT`。
4. 写入前的校验：请求里有未定义的字段返回 400；值的类型转不过去、必填没填、枚举值不在选项里，返回 400 并带 `fieldErrors`；没传的字段取默认值。系统字段由服务端写，请求里带了就忽略。
5. 唯一冲突：捕获 `DuplicateKeyException`，从索引名反查出是哪个字段，返回 409 并带 `fieldErrors`。
6. 读出：用 B2 的 `FieldTypeHandler` 把列值转成契约规定的 JSON 值。
7. 把新建、修改、删除写成固定的流程：前置钩子 → 校验 → 写库 → 后置钩子 → 读回。钩子现在是空方法，B5 接上脚本。这是模板方法模式，记下为什么这样组织。

**验收标准**

- [ ] 新建物料只传 `name`，返回的记录带 `id`，`category` 是 `raw`，`unit` 是“个”。
- [ ] 不传 `name`，返回 400，`fieldErrors.name` 有提示。
- [ ] 新建两条 `code` 相同的记录，第二条返回 409，`fieldErrors.code` 有提示。
- [ ] 修改时只传 `spec`，其它字段不变，`updated_at` 变了。
- [ ] 查询：`like`、`in`、排序、第 2 页都正确，`total` 正确。
- [ ] 注入测试一：`filters` 里的 `field` 传 `name; DROP TABLE md_material`，返回 400，表还在。
- [ ] 注入测试二：`value` 传 `' OR '1'='1`，被当成普通字符串，查不到记录。
- [ ] 注入测试三：`sort` 里的 `order` 传 `desc; drop table`，返回 400。
- [ ] 模型名不存在时，各接口都返回 404。
- [ ] 新建一个模型后，不重启就能对它调用这些接口。
- [ ] `SqlBuilder` 对非法字段名、非法运算符各有一条单元测试。

## B4 关联关系

**目标：** 多对一和一对多可用，产品和 BOM 能跑通。预计 2 小时。

**要记录的思考**

- 决策 009（和前端一起定）：关联关系怎么表达。
  - 多对一字段在响应里为什么返回 `{ id, label }`，而不是只返回 `id`，或者返回整条目标记录？
  - 一对多为什么不做“保存产品时一起保存 BOM 明细”，而是让子表记录单独增删改？
  - 为什么不建数据库外键？
  - 取 `label` 时，为什么用“收集 id 后一次 `IN` 查询”，而不是每条记录查一次，或者直接 `JOIN`？

**步骤**

1. 写入：`manyToOne` 字段接受 `id`，也接受 `{ id, ... }`。目标记录不存在时返回 400 并带 `fieldErrors`。
2. 读出：把一页记录里同一个关联字段的 `id` 收集起来，用一条 `WHERE id IN (...)` 取回显示字段，再组装成 `{ id, label }`。
3. `options` 接口：按 `displayField` 模糊匹配，返回 `value` 和 `label`。`displayField` 也要过白名单。
4. 删除保护：删记录前，从 `MetaRegistry` 找出所有指向本模型的 `manyToOne` 字段，逐个检查有没有记录引用它，有就返回 409，并说明被哪个模型引用。删模型时同理。
5. 一对多不用写新接口，确认“按 `mappedBy` 字段等于某个 id 查询子表”可用即可。

**验收标准**

- [ ] 查询产品 BOM，`product` 和 `material` 都是 `{ id, label }`。
- [ ] 新建 BOM 时 `material` 传一个不存在的 id，返回 400，`fieldErrors.material` 有提示。
- [ ] 按 `product` 等于 1 查询 BOM，只返回这个产品的明细。
- [ ] 删除一个被 BOM 引用的物料，返回 409，提示里提到“产品 BOM”。
- [ ] `options` 带 `keyword` 和 `displayField` 能搜到。
- [ ] 查询一页 10 条 BOM 时，后端执行的 SQL 条数是固定的，不随记录数增加。把日志截图留作证据。

## B5 服务引擎

**目标：** 开发者定义的脚本服务能执行，包括手动调用和生命周期钩子；用它实现编码规则。预计 3 小时。

**要记录的思考**

- 决策 006：脚本引擎选哪个。候选至少包括 Groovy 和 AviatorScript（IIDP 的规则引擎用的就是 Aviator），也可以看 SpEL。
  - 比较这几点：能不能写多条语句和循环；脚本里怎么读写数据库；能不能限制脚本做危险的事；依赖包的大小；学习成本。
  - 试做：用两个引擎各写一遍“生成编码”的脚本，把两份脚本都贴进决策记录，然后再选。没选的那份留在一个单独的 git 分支上。
- 还要想：脚本里为什么只给一个受控的 `db` 对象，而不是直接给 `JdbcTemplate`？脚本死循环了怎么办？这两点即使不实现，也把想法写下来。

**步骤**

1. 定义接口 `ScriptEngine`（输入脚本文本和上下文，输出返回值），写一个实现。业务代码只依赖接口，以后换引擎不用改别处。
2. 脚本上下文里提供：
   - `record`：当前记录，前置钩子里可以修改它。
   - `params`：调用方传的参数。
   - `db`：受控的数据访问对象，内部走 B3 的通用数据服务，所以脚本的读写同样受校验和白名单保护。至少要有按 id 读取、条件查询、修改这几个方法，再加一个“把某个整数字段原子地加 1 并返回新值”的方法，编码规则要用。
   - 调用其它服务的方法。
3. 服务接口 `POST /api/svc/{model}/{service}`：只允许调用 `trigger` 为 `manual` 的服务。
4. 钩子：在 B3 留的钩子位置，执行这个模型上对应 `trigger` 且启用的服务。前置钩子对 `record` 的修改要生效；`beforeDelete` 里抛错要能阻止删除。
5. 事务：一次保存里的钩子和写库放在同一个事务里，脚本出错时整体回滚。
6. 把 `samples/mes.json` 里三段“待改写”的脚本改成真正的脚本：编码规则的 `generate`，物料和产品的 `fill_code`。生成编码时流水号的自增必须是原子的。
7. 在 [meta-model.md](../contract/meta-model.md) 的“服务”一节补上：脚本用什么语言、有哪些变量和方法、一个完整例子。这是改契约，按契约的修改规则提 PR 并通知前端。

**验收标准**

- [ ] 对一条前缀为 `MAT-`、日期格式为年月日、流水号 4 位的规则调用 `generate`，返回形如 `MAT-20261115-0001`；再调一次是 `0002`；规则记录里的 `current_serial` 同步变化。
- [ ] 新建物料不传 `code`，保存后自动有编码；传了 `code` 就用传入的。
- [ ] 并发测试：同时发 20 个新建物料的请求，得到 20 个互不相同的编码。写成一个测试或脚本，留在仓库里。
- [ ] 脚本有语法错误或运行出错时，返回 400，`message` 能看出错在哪；这次保存没有写进数据库。
- [ ] 调用一个不是 `manual` 的服务，返回 404。
- [ ] 修改脚本后不重启，下一次调用就是新逻辑。
- [ ] 契约文档已经补上脚本说明。

## B6 热加载和导入导出

**目标：** 元模型的任何改动都立刻生效；导入是原子的。预计 1 小时。

**要记录的思考**

- 决策 010：元模型改了以后怎么让各处都知道。
  - 内存注册表和数据库谁先更新？中间失败了会不会不一致？
  - 现在只有一个后端实例。如果部署两个实例，会出什么问题？不用实现，写下你会怎么解决。
  - 前端怎么知道菜单变了？

**步骤**

1. 检查从“保存模型”到“数据接口可用”的整条链路，确认没有任何地方需要重启。
2. 导入的原子性：先对整个包做完校验，全部通过才开始执行；元模型表的写入放在一个事务里。建表不能回滚，把这个局限和你的处理方式写进决策 010。
3. 可选：实现 `GET /api/openapi.json`，根据当前的元模型生成每个模型的接口描述。这是“平台确实动态生成了 api”最直观的证据，演示时很有说服力。

**验收标准**

- [ ] 全程不重启：新建模型 → 菜单接口里出现 → 数据接口可用 → 给模型加字段 → 新字段立刻可读写。
- [ ] 把 `export` 的结果原样 `import` 回去，所有模型不变。
- [ ] 导入一个第 2 个模型有错误的包，返回 400，第 1 个模型也没有被创建。
- [ ] 清空数据库后导入 `mes.json`，能完整恢复。

## B7 AI 助手（加分项）

联调 2 通过之后再做。**目标：** 用一句话描述生成元模型包。预计 2 到 3 小时。

**要记录的思考**

- 决策 011：
  - 上个项目 ai-agent-project 是让 AI 生成代码，这次让 AI 只生成元模型。两种做法在可校验性、出错后的影响范围、部署方式上有什么不同？
  - 为什么生成的结果不直接保存，而要人确认？
  - AI 的输出为什么要当成不可信的输入来校验？这和决策 004 是什么关系？

**步骤**
