## 2.1 元模型的定义本身怎么存

- 负责人：后端（组长）
- 关联任务：B1
- 状态：已定，选方案 B
- 最后更新：2026-11-14

这份记录里的“候选方案”和“试做和测试”是 2026-11-14 由组长使用 Claude Code 起草的。“结论”“讨论记录”“代价和反思”由组长填写。

### 2.1.1 问题

开发者在设计器里定义的模型（有哪些字段、什么视图、什么服务）要保存在数据库里。这些“描述模型的数据”自己用什么结构存？

它值得认真想，是因为后面所有功能都要读它：建表、通用接口、菜单、导入导出、AI 助手。存法选得别扭，每个功能都会跟着别扭。

注意这个问题和 002 不是一回事。002 问的是业务数据（物料、产品的记录）怎么存，这里问的是模型定义怎么存。

### 2.1.2 候选方案

| 方案 | 怎么做 | 好处 | 代价 |
|---|---|---|---|
| A 拆成多张表 | 模型、字段、服务、视图各一张表，一个字段一行 | 能用 SQL 直接查“哪些模型有多对一字段”这类问题；数据库能保证同一模型内字段名不重复 | 保存和读取都要操作多张表再组装；模型定义每加一种配置项都要改表结构；枚举选项和视图配置还是得存成 JSON 或再拆表 |
| B 每个模型一份 JSON | 模块一张表，模型一张表；模型表里一列存整个定义的 JSON 文本 | 存取各一条 SQL；和接口契约、导入导出、AI 生成的格式是同一份东西，不用拆装；定义加配置项不用改表 | 不能用 SQL 按字段查询；字段名不重复这类规则只能靠程序校验 |

### 2.1.3 试做和测试

用示例里的“物料”模型来比：8 个字段，1 个服务，列表和表单 2 个视图。

**方案 A 的建表语句**

```sql
CREATE TABLE meta_model (
  name          VARCHAR(30) PRIMARY KEY,
  module_name   VARCHAR(30)  NOT NULL,
  display_name  VARCHAR(100) NOT NULL,
  description   VARCHAR(500),
  show_in_menu  TINYINT(1)   NOT NULL DEFAULT 1,
  sort          INT          NOT NULL DEFAULT 100
);

CREATE TABLE meta_field (
  id             BIGINT AUTO_INCREMENT PRIMARY KEY,
  model_name     VARCHAR(30)  NOT NULL,
  name           VARCHAR(30)  NOT NULL,
  display_name   VARCHAR(100) NOT NULL,
  type           VARCHAR(20)  NOT NULL,
  required       TINYINT(1),
  is_unique      TINYINT(1),
  readonly       TINYINT(1),
  default_value  VARCHAR(500),
  length         INT,
  precision_     INT,
  scale          INT,
  options        TEXT,          -- 枚举选项：要么存成 JSON，要么再拆一张表
  relation_model VARCHAR(30),
  display_field  VARCHAR(30),
  mapped_by      VARCHAR(30),
  position       INT NOT NULL,  -- 字段的先后顺序
  UNIQUE KEY uk_meta_field (model_name, name)
);

CREATE TABLE meta_service (
  id           BIGINT AUTO_INCREMENT PRIMARY KEY,
  model_name   VARCHAR(30)  NOT NULL,
  name         VARCHAR(30)  NOT NULL,
  display_name VARCHAR(100) NOT NULL,
  trigger_     VARCHAR(20)  NOT NULL,
  scope        VARCHAR(10),
  script       TEXT         NOT NULL,
  enabled      TINYINT(1)   NOT NULL DEFAULT 1,
  position     INT          NOT NULL
);

CREATE TABLE meta_view (
  model_name VARCHAR(30) NOT NULL,
  type       VARCHAR(10) NOT NULL,  -- list 或 form
  config     TEXT        NOT NULL,  -- 视图配置：要么存成 JSON，要么再拆两三张表
  PRIMARY KEY (model_name, type)
);
```

**方案 B 的建表语句**

```sql
CREATE TABLE meta_module (
  name         VARCHAR(30) PRIMARY KEY,
  display_name VARCHAR(100) NOT NULL,
  icon         VARCHAR(50),
  sort         INT NOT NULL DEFAULT 100
);

CREATE TABLE meta_model (
  name        VARCHAR(30) PRIMARY KEY,
  module_name VARCHAR(30) NOT NULL,
  definition  MEDIUMTEXT  NOT NULL,  -- 整个模型定义的 JSON
  created_at  DATETIME    NOT NULL,
  updated_at  DATETIME    NOT NULL
);
```

**保存和读取“物料”模型各要几条 SQL**

| 操作 | 方案 A | 方案 B |
|---|---|---|
| 新建 | 12 条 INSERT：模型 1、字段 8、服务 1、视图 2 | 1 条 INSERT |
| 修改（设计器是整份保存的） | 15 条：1 条 UPDATE，3 条 DELETE 清掉旧的字段、服务、视图，再 11 条 INSERT | 1 条 UPDATE |
| 读取 | 4 条 SELECT，再在程序里组装成一个定义 | 1 条 SELECT，再解析 JSON |

: 表 2-2 试做和测试


**试做中注意到的几点**

- 方案 A 里，枚举选项和视图配置仍然要存成 JSON，否则还得再加三四张表。也就是说方案 A 并不能完全避开 JSON。
- 方案 A 能用 SQL 查字段。但所有模型定义启动时都会加载到内存里，“哪些模型引用了物料”这类问题在程序里遍历就能回答。校验器里“被引用的字段不能删”这条规则就是这么做的，已经有测试。
- 方案 B 里“字段名不重复”没有数据库约束兜底，全靠 `MetaValidator`。这条规则也已经有测试。
- 接口契约规定修改模型时提交完整的定义，所以两种方案下，两个人同时改同一个模型都是后保存的覆盖先保存的，这一点没有区别。

**按方案 B 实现之后的结果（2026-11-14）**

- 存取层 `MetaRepository` 里，新建一个模型是 1 条 INSERT，修改是 1 条 UPDATE，和试做时数的一致。
- 连本机 MySQL 实测：导入契约示例的 2 个模块、4 个模型一次成功；重启后端后定义都还在。
- 导入导出不需要任何拆装代码：导出的结果原样导入回去，再导出，两次内容完全相同（有测试）。
- 方案 B 的代价确实出现了：数据库里看不出一个模型有哪些字段，只能看到一段 JSON。排查问题时要把 JSON 拿出来看，或者调 `/api/meta/models/模型名` 接口。

- 负责人：后端（组长）
- 关联任务：B2
- 状态：已定，选方案 A（每个模型一张真实的表）
- 最后更新：2026-11-14

### 2.2.1 问题

物料、产品这些业务记录在数据库里用什么结构存。难点是：有哪些模型、每个模型有哪些字段，都是运行时在页面上定义的，写代码时不知道。

这个问题和 001 不是一回事。001 问的是模型定义怎么存，这里问的是按定义录入的业务数据怎么存。

### 2.2.2 候选方案

| 方案 | 怎么做 | 好处 | 代价 |
|---|---|---|---|
| A 每个模型一张真实的表 | 物料就是一张物料表，一个字段一列 | 搜索、排序、分页就是普通 SQL；唯一约束直接交给数据库；打开数据库就能看懂数据；课上的 IIDP 也是这样 | 模型一改就要改表结构，而改表语句不能回滚（见决策 005） |
| B 一张大表存所有字段值（EAV） | 一行存“哪条记录的哪个字段是什么值” | 不用建表改表，加字段零成本 | 按字段搜索和排序要自己和自己关联；所有值只能存成文本；唯一约束没法用普通索引表达 |
| C 每条记录一段 JSON | 一张通用表，记录整体放在 JSON 列里 | 不用改表 | 按字段查询要用数据库的 JSON 函数，用不上普通索引；要保证唯一还得给每个字段建生成列和索引，等于还是要改表 |

### 2.2.3 试做和测试

用同一个需求来比：**在物料里按名称模糊搜索“螺丝”，按安全库存从大到小排，取前 10 条；并且保证物料编码不重复。**

**方案 A**

```sql
SELECT * FROM md_material
WHERE name LIKE '%螺丝%'
ORDER BY safety_stock DESC
LIMIT 10;

-- 编码不重复：建表时一句话
CONSTRAINT uk_material_code UNIQUE (code)
```

**方案 B**

```sql
-- 假设大表是 data_value(record_id, model, field, value_text)
SELECT n.record_id
FROM data_value n
JOIN data_value s ON s.record_id = n.record_id AND s.field = 'safety_stock'
WHERE n.model = 'material' AND n.field = 'name' AND n.value_text LIKE '%螺丝%'
ORDER BY CAST(s.value_text AS DECIMAL(18,2)) DESC
LIMIT 10;
-- 这只拿到了 10 个记录号。还要再查一次，把这 10 条记录的所有字段取出来，在程序里拼回一行一行。
-- 每多一个搜索条件或排序字段，就要多关联一次这张大表。

-- 编码不重复：没法用普通的唯一索引。只能程序里“先查有没有，再插入”，两个请求同时来时会都通过。
```

**方案 C**

```sql
-- 假设通用表是 data_record(id, model, data JSON)
SELECT * FROM data_record
WHERE model = 'material'
  AND JSON_UNQUOTE(JSON_EXTRACT(data, '$.name')) LIKE '%螺丝%'
ORDER BY CAST(JSON_EXTRACT(data, '$.safety_stock') AS DECIMAL(18,2)) DESC
LIMIT 10;

-- 编码不重复：要给 code 建一个生成列再加唯一索引，这本身就是一次改表。
```

**按方案 A 实现之后，在本机 MySQL 上实测的结果（2026-11-14）**

- 导入契约示例后，数据库里出现四张表：`md_material`、`md_product`、`md_product_bom`、`md_code_rule`。
- 物料表的列和类型：`code varchar(64)`、`name varchar(100)`、`category varchar(64)`、`safety_stock decimal(18,2)`、`enabled tinyint(1)`、`remark text` 等，`code` 上有唯一索引。
- 唯一约束确实由数据库把关：直接用 SQL 往表里插入重复的值，被数据库拒绝。
- 一对多字段（产品的“BOM 明细”）不占列；多对一字段（BOM 的“产品”“物料”）是存对方 id 的 `bigint` 列。

字段类型和列类型的对应关系写成了“每种类型一个处理类”（`backend/.../schema/types/`），由 `FieldTypeRegistry` 按类型名查找。以后加一种字段类型，只要加一个类、登记一行。

## 2.3 “动态生成 api”怎么实现

- 负责人：后端（组长）
- 关联任务：B3
- 状态：已定，选方案 A（一个通用控制器）
- 最后更新：2026-11-15

### 2.3.1 问题

课题要求“平台可以动态加载元模型定义信息，动态生成 api”。元模型是运行时在页面上定义的，写代码时不知道会有哪些模型、哪些字段，所以数据接口不能像普通项目那样一个模型写一个 Controller。要决定的是：接口怎么做到“新建一个模型，它的增删改查立刻可用，不用重启”。

### 2.3.2 候选方案

| 方案 | 怎么做 | 好处 | 代价 |
|---|---|---|---|
| A 一个通用控制器 | `DataController` 上写 `@RequestMapping("/api/data/{model}")`，模型名是路径变量。每次请求去内存注册表里查模型定义，再按定义拼 SQL | 实现简单，一个类五个方法；模型删了不用清理任何映射；接口文档只有一份；新建模型后接口立刻能用 | 所有模型的接口在地址上长得一样，只能靠路径区分；没法给单个模型加特殊接口 |

## 2.4 表名和列名要拼进 SQL，怎么防注入

- 负责人：后端（组长）
- 关联任务：B3
- 状态：已定，按四条白名单规则实现
- 最后更新：2026-11-15

### 2.4.1 问题

数据接口要按元模型拼 SQL。值和以前一样可以用参数绑定，但**表名、列名、排序方向没法当参数**——SQL 预编译只允许把“值”当参数，表名列名必须是语句的一部分。所以一部分字符串注定要拼进 SQL，问题是拼什么、怎么保证拼进去的只有我们认可的东西。

这在普通项目里不是问题：表名列名是写死在代码里的。这里它们是用户在页面上定义的，请求里的字段名也来自前端，两者都不能直接信。

### 2.4.2 候选方案

| 方案 | 怎么做 | 好处 | 代价 |
|---|---|---|---|
| A 白名单：只拼“定义里有的” | 表名列名只从校验过的模型定义里取；请求里的字段名只用来在定义里查找；运算符、排序方向用 `switch` 映射；拼之前再加反引号并复查标识规则 | 规则简单、可检查；注入请求的结果是 400，而不是“看起来像正常查询” | 每加一种请求形态（新的比较方式）都要在映射表里登记 |
| B 转义/过滤特殊字符 | 把表名列名里的引号、分号去掉再拼 | 实现快 | 黑名单永远漏；去字符之后可能变成另一个合法名字，出错难查 |
| C 只用参数绑定 | 想办法把表名也做成参数 | 不用关心拼接 | SQL 语法不支持；用字符串函数拼表名等于还是拼 |

### 2.4.3 试做和测试

按方案 A 实现，规则写在 `backend/src/main/java/com/metaforge/data/SqlBuilder.java` 的类注释里。四条规则分别防的是：

1. **表名、列名只从模型定义里取。** 请求里的字段名只拿去 `model.findField(name)`，查不到就 400。防的是“把 SQL 片段当字段名带进来”：`{"field": "name; DROP TABLE md_material"}` 在定义里查不到，直接拒绝。
2. **值一律走命名参数。** 防的是值注入：`{"field": "name", "op": "eq", "value": "' OR '1'='1"}` 会被当成普通字符串，查不到记录。
3. **比较方式、排序方向用 `switch` 映射成固定几种写法。** 防的是在结构位置注入：`{"order": "desc; drop table"}` 匹配不到 `asc`/`desc`，返回 400。
4. **拼进 SQL 之前再用标识规则查一遍并加反引号。** 防的是“前面漏了校验”或者“元模型 JSON 被手改过”：名字不满足 `^[a-z][a-z0-9_]*$` 就不拼进 SQL。这是第二道，正常路径上不会触发。

| 过滤的值传 `' OR '1'='1` | 200，`total = 0`（`injectionInFilterValueIsTreatedAsPlainText`） |
| 排序方向传 `desc; drop table md_material` | 400，表还在（`injectionInSortOrderIsRejected`） |
| 单测：非法字段名、非法运算符、非法排序方向各一条 | `SqlBuilderTest` |
| 名字里带分号的标识 | `SqlBuilder.quote` 直接 400（`SqlBuilderTest.unsafeIdentifierIsRejectedBeforeReachingSql`） |

四句话的版本（可以直接讲给老师听）：**表名列名只来自定义、值只走参数、运算符和排序方向只认白名单、拼之前再查一遍名字格式。** 每一条挡的攻击不一样，少一条都能构造出例子。

### 2.4.6 代价和反思

- 白名单的思想是“不认识就拒绝”，所以前端每加一种查询写法（比如以后要 `between`），后端都要同步登记，否则前端拿到 400。这个耦合是有意的。
- `like` 的 `%`、`_` 要转义，否则用户搜 `100%` 会变成“任意开头结尾”，这是通配符注入，不是 SQL 注入，但同样是“值被当成了语法”。现在的做法是把值里的 `%`、`_`、`\` 加上反斜杠再包一层 `%`（契约里 `like` 的含义是“包含”）。
- `SqlBuilder` 和 `DdlBuilder` 各留了一份标识规则。为什么不合成一处：它们分属“建表”和“读写数据”两个环节，抽公共方法要把 data 包的检查搬到 schema 包（或反过来），十行代码换一次跨包依赖，不划算。这条如果被问“为什么不 DRY”，可以如实回答。

## 2.5 模型改了以后，已有的表和数据怎么办

- 负责人：后端（组长）
- 关联任务：B2
- 状态：已定，按下面“目前的做法”
- 最后更新：2026-11-14

这份记录里的“候选方案”“试做和测试”是 2026-11-14 由组长使用 Claude Code 起草的。让组长选方案的弹窗两次被中断，Claude Code 先按它建议的做法实现了。组长确认或改选之后，把“结论”补上。

### 2.5.1 问题

业务数据存在真实的表里（决策 002），所以模型一改，表就要跟着改。难处在于 MySQL 的建表、改表语句一执行就生效，不能回滚。要回答这几个小问题：

1. 加字段时，已有的数据在新列上是什么值？
2. 删字段时，那一列和里面的数据删不删？
3. “必填”用数据库的 `NOT NULL` 保证，还是只在程序里校验？
4. “唯一”由谁保证？
5. 已有字段能改什么、不能改什么？
6. 删模型时，表删不删？
7. “改表”和“保存定义”哪个先做？中途失败了怎么办？

### 2.5.2 候选方案和目前的做法

| 小问题 | 候选 | 目前的做法和理由 |
|---|---|---|
| 1 加字段 | 新列填默认值；新列为空 | 新列为空。默认值只在以后新建记录时生效，不回头改已有数据 |
| 2 删字段 | 直接删列；列原样留着；列改名留作备份 | 列改名为 `zz_字段名_时间`。直接删列数据就找不回来了；原样留着的话，以后再加一个同名字段会冲突 |
| 3 必填 | 数据库 `NOT NULL`；程序校验 | 程序校验，所有业务列都允许为空。如果用 `NOT NULL`，加一个必填字段时老数据没有值，这一列根本加不上 |
| 4 唯一 | 程序先查再插；数据库唯一约束 | 数据库唯一约束。程序先查再插，两个请求同时来时会都通过 |
| 5 改已有字段 | | 类型不让改（校验器拒绝）。长度和精度可以改；是否唯一可以改 |
| 6 删模型 | 直接删表；表改名留作备份 | 表改名为 `zz_模型名_时间`。演示或开发时误删一个模型，数据还能找回来 |
| 7 先后顺序 | 先存定义再改表；先改表再存定义 | 先校验，再改表，改成功了才存定义。改表失败时定义还是旧的，表和定义仍然对得上 |

: 表 2-11 候选方案和目前的做法


改表的多个步骤里，可能因为已有数据而失败的（给已有的列加唯一约束、改已有列的长度）排在最前面执行。这样它们失败时，表还一点都没动过。

导入一个包时分三段：先把整个包校验完；再建表改表；最后在一个事务里保存所有定义。中途失败时，把这一次新建的表删掉。

**试做中发现并修掉的两个问题**

1. **备份的名字重复。** 备份表的名字后缀一开始只精确到秒。验收脚本在同一秒内把“供应商”模型删除、重建、又删除，第二次删除时备份表重名，改名失败，接口返回 500。改成精确到毫秒后解决，并加了“连续新建、删除三次”的测试。
2. **表和定义对不上时会卡死。** 上面那次失败留下了“定义还在、表却没有了”的状态，这个模型从此删不掉也建不了。说明“先改表再存定义”只能减少对不上的情况，不能完全避免。现在的处理：删模型时如果表已经不在了，就跳过改名，继续删定义；建模型时如果已经有一张同名的表却没有对应的定义，先把那张表改名备份，再建新表。这两种情况都加了测试，也在真实 MySQL 上验过。

- 备份列和备份表不会自动清理，时间长了要手工删。

## 2.7 前端动态路由怎么做

- 负责人：前端
- 关联任务：F1 菜单和动态路由
- 状态：已定
- 最后更新：2026-11-14

### 2.7.1 问题

MetaForge 的业务模型是运行时才确定的：开发者可以在页面上新建模型，模型会出现在菜单里，点进去是 `/app/{模型名}` 这样的地址。前端不能在代码里把每个模型的路由写死，需要一种按菜单动态注册路由的方式。要决定的是：用一条带参数的固定路由 `/app/:model`，还是按菜单逐个 `addRoute` 注册。

### 2.7.2 候选方案

| 方案 | 怎么做 | 好处 | 代价 |
|---|---|---|---|
| A：一条参数路由 `/app/:model` | 在固定路由表里写一条 `{ path: '/app/:model', component: ModelListPage }`，页面里用 `useRoute().params.model` 取模型名 | 代码最少，只写一条路由，不随模型数量变化；刷新页面不用重新注册路由 | 无法区分“合法模型”和“乱写的地址”，`/app/abc` 也会渲染列表页而不是 404；顶部标题、菜单高亮等都要再按模型名查一次菜单才能得到 |
| B：按菜单逐个 `addRoute` 注册 | 拿到菜单后，对每个叶子节点调 `router.addRoute('layout', {...})`，注册成带 `meta.title` 的真实路由 | 只有菜单里存在的模型才有路由，`/app/abc` 自然落到 404；每个路由自带 `meta.title` 和 `props.model`，标题、高亮、传参都更直接 | 要多维护一份“注册过的路由名”列表，reload 时要先 `removeRoute`；刷新页面时路由还没注册，需要全局守卫在首次导航前先加载菜单 |

: 表 2-17 候选方案


### 2.7.3 试做和测试

在 `feat/f1` 分支上实现方案 B。要点：

- 菜单 store 的 `load()` 对每个叶子节点 `addRoute`，并把注册过的路由名记进数组；`reload()` 按名 `removeRoute` 后重新加载。
- `router.beforeEach` 里若菜单未加载，先 `await load()`，再 `return to.fullPath` 让这次导航重新匹配一遍。

关键片段：

```ts

  const menuStore = useMenuStore()
  if (!menuStore.loaded) {
    await menuStore.load()
    // 动态路由刚注册好，让这次跳转重新匹配一遍
    return to.fullPath
  }
})
```

### 2.7.5 结论

选了 B（按菜单逐个 `addRoute` 注册）。决定性的理由：本项目是模型驱动的低代码平台，模型的增删是常态，菜单本身就是“哪些地址合法”的唯一依据——按菜单注册，`/app/abc` 这类地址会自然落到 404，而且每个路由自带的 `meta.title` 直接驱动顶部标题和菜单高亮，不必再按模型名二次查表。A 方案“代码最少”的优势，在“要能区分合法/非法地址、要正确显示标题”这两个需求面前站不住。

## 2.8 视图怎么渲染

- 负责人：前端
- 关联任务：F3 通用表单
- 状态：已定
- 最后更新：2026-11-14

### 2.8.1 问题

通用表单要能渲染任意模型的字段，而每个字段的类型不同，对应的输入控件也不同（`string` 用输入框、`enum` 用下拉、`boolean` 用开关……）。要决定的是：在表单组件里用一长串 `v-if` 按字段类型挑控件，还是维护一张「字段类型 → 组件」的注册表，用 `<component :is>` 动态渲染。

### 2.8.2 候选方案

| 方案 | 怎么做 | 好处 | 代价 |
|---|---|---|---|
| A：一长串 v-if | 在 ModelForm 模板里写 `<a-input v-if="field.type==='string'">`、`<a-select v-else-if="field.type==='enum'">`……每种类型一个分支 | 一眼就能看到所有控件，不用额外理解注册表 | 分支越写越长；新增一种字段类型要回到模板改、容易漏改、破坏现有分支；控件细节（如清空发 null）散落各处难以复用 |
| B：字段类型到组件的注册表 | 把每种字段类型抽成一个字段组件（统一 props/事件），在 `fields/index.ts` 建一张 `fieldComponents` 映射，表单里统一 `<component :is="fieldComponents[field.type]">` | 新增类型只加一个组件 + 注册表一行，表单不用动；控件逻辑封装在各自组件里，可复用 | 多一层抽象，初次理解成本略高 |

### 2.8.5 结论

## 2.9 关联关系怎么表达

- 负责人：后端（组长）、前端
- 关联任务：B4、F4
- 状态：已定
- 最后更新：2026-11-17

### 2.9.1 问题

模型之间会有两种关联：多对一（产品 BOM 里的“物料”指向一条物料）和一对多（产品里的“BOM 明细”是一组产品 BOM）。要决定四件事：

1. 多对一字段在响应里返回什么：只返回 id、返回整条目标记录，还是别的形式。
2. 一对多怎么保存：保存产品时一起保存明细，还是明细单独增删改。
3. 要不要建数据库外键来保证引用完整性。
4. 多对一的显示文字（label）怎么取，才能既不逐条查，也不把 SQL 写得太复杂。

### 2.9.2 候选方案

| 小问题 | 方案 | 做法 | 好处 | 代价 |
|---|---|---|---|---|
| 1 多对一返回什么 | A | 只返回 id | 响应小 | 列表要显示名称时前端得再查，一页 10 条就是 10 次请求 |
| 1 | B | 返回整条目标记录 | 前端什么都有 | 列表只用得着名称，却把所有字段甚至目标记录的关联一起带过来 |
| 1 | **C（选）** | 返回 `{ "id": 3, "label": "螺丝 M3" }` | 一个字段既够显示又够提交，列表不用补查 | 后端要多查一次 label |
| 2 一对多怎么保存 | A | 保存产品时级联保存明细 | 前端一次提交 | 前端要记新增/修改/删除，后端要多表事务，部分失败时整张表单白填 |
| 2 | **B（选）** | 明细单独调子表模型的接口增删改 | 每个接口只做一张表，失败范围小 | 新建产品要先保存，才能加明细 |
| 3 要不要外键 | A | 建数据库外键 | 数据库兜底 | 改表是“改名留备份”，外键会挡着；删被引用记录时数据库只给笼统错误，说不出被谁引用 |
| 3 | **B（选）** | 不建外键，写入查目标存在、删除查引用 | 改表和备份不受外键约束；错误能说清是哪条引用 | 脏数据要靠程序兜住，应用层多两次查询 |
| 4 label 怎么取 | A | 每条记录查一次目标表 | 实现简单 | 一页 N 条就是 N 次查询 |
| 4 | B | JOIN 目标表 | 一条 SQL | 表名列名运行时拼，JOIN 要处理重名和关联不存在；一个 JOIN 只能带一个显示字段 |
| 4 | **C（选）** | 收集这一页同一关联字段的 id，一条 `WHERE id IN (...)` 取回，再拼 `{id,label}` | 查询条数只跟关联字段数有关，跟记录数无关 | 每个关联字段多一条查询 |

## 2.10 元模型改了以后怎么立刻生效

- 负责人：后端、前端
- 关联任务：B6、F5
- 状态：已定
- 最后更新：2026-11-22

### 2.10.1 问题

元模型存在数据库里，后端内存里还有一份 `MetaRegistry` 快照。改完模型后要马上能读能写，不能重启；要回答：

1. 数据库和内存谁先更新？中间失败了会不会不一致？
2. 导入一个包时，建表不能回滚，怎么保证不留下“改了一半”的状态？
3. 前端怎么知道菜单变了？
4. 如果部署两个后端实例，会出什么问题？

### 2.10.2 决策

#### 2.10.2.1 数据库是唯一事实来源，先写库再刷新内存

保存模型/模块的顺序固定为：

```text
校验 → 写数据库（元模型表）→ MetaRegistry.reload() → 返回
```

- `MetaRegistry.reload()` 从数据库整份重读模块和模型，组装成一份新的不可变快照，再一次性替换。
- 写库失败：不刷新内存，旧快照继续服务。
- 刷新失败：数据库里已经是新定义，但当前内存还是旧快照；错误返回给调用方，下一次成功的 `reload()` 会恢复一致。数据库是唯一事实来源，内存只是缓存。
- 不采用“先改内存再写库”：写库失败时内存里会有一个数据库里不存在的模型，数据接口会对着不存在的表读写。

#### 2.10.2.2 导入的原子性

导入一个 `MetaBundle` 分三步：

1. **先校验整个包**：模块、模型、字段、关联、服务、视图全部过 `MetaValidator`；有一处错就整个拒绝，此时还没动数据库。
2. **建表/改表**：新模型建表；已有模型按字段差异改表。
3. **写定义**：所有模块和模型的定义放在一个事务里，要么全成功，要么全失败。

限制和补偿：

- DDL 不能回滚。第 2 步如果建了新表、第 3 步写定义失败，代码会把这次新建的表删掉，不留下没人认领的表。
- 已经存在的老表如果被 `ALTER TABLE` 改到一半失败，数据库无法自动还原；这是 MySQL DDL 的固有限制。演示和正式导入前先备份数据库；代码保证“定义表不写一半”，并尽量把新建表清掉。
- 导入前不做“先删旧定义再建新定义”，否则第 2 步失败会把旧系统也弄坏。

#### 2.10.2.3 前端怎么知道菜单变了

- 保存模型后，F5 设计器调用 `useMenuStore.reload()`：先按名字移除旧动态路由，再请求 `/api/meta/menus`，按新菜单重新 `addRoute`。
- 菜单接口本身每次请求都从 `MetaRegistry` 读当前快照，所以新模型立刻出现在菜单里。
- 不采用轮询：课程场景只有三个人用，保存后主动 reload 足够；轮询会增加无意义请求。
- 已经打开的其他页面如果引用了被删字段，刷新页面即可；不要求做实时推送。

#### 2.10.2.4 多实例部署（只写思路，不实现）

现在只有一个后端进程，每个进程都有自己的 `MetaRegistry`。如果部署两个实例：

- 实例 A 保存模型，只刷新 A 的快照；实例 B 仍用旧快照，会出现“一会儿能读、一会儿 404”。
- 解决方向：保存成功后往 Redis 发布一条“元模型版本变了”的消息，各实例订阅后各自 `reload()`；或者用数据库里的版本号 + 定时轮询。
- 还要处理并发保存：用数据库版本号做乐观锁，避免两个实例同时改同一模型互相覆盖。
- 这是部署层问题，B6 不实现；单实例下先保证正确。

## 2.12 数据访问为什么用 JdbcTemplate

这个项目特殊的地方：业务模型（物料、产品）是运行时在页面上定义的，编译的时候根本不知道会有哪些表、哪些列，所以没有对应的 Java 实体类。

### 2.12.2 候选方案

### 2.12.5 结论

选 **C：Spring `JdbcTemplate` / `NamedParameterJdbcTemplate`**。

理由：

1. 业务模型是运行时定义的，没有编译期实体类；ORM 最核心的“实体类 ↔ 表”映射用不上。
2. 这个项目的核心正是“按元模型生成 SQL”。表名、列名、条件、排序都由 `SqlBuilder` 从校验过的模型定义生成，SQL 完全可控，也方便针对注入写单元测试（决策 004）。
3. Spring Boot 自带，不增加依赖；事务、连接池、异常转换已经够用。
4. MyBatis-Flex 没有实体类时可以用 `Db` + `Row` 做动态查询，但这会引入一套组员不熟的新 API 和额外依赖；元模型表只有 `meta_module`、`meta_model` 两张，为它们引入 ORM 的收益也很小。
5. JPA 完全围绕实体类，运行时才出现的表基本没法用，直接排除。

准确说法不是“MyBatis-Flex 做不到”，而是“在这个场景下它的收益不值得”。如果以后做的是模型固定、实体很多的管理系统，ORM 会更省事。

### 2.12.6 代价和反思

- 没有自动映射：数据库行要自己转成 `Map`/JSON，多对一还要额外拼 `{id,label}`；这些代码集中在 `DataService`/`SqlBuilder`，没有散落到各个接口。
- SQL 自己拼：防注入要自己负责。我们用“标识白名单 + 参数绑定 + 操作符 switch + 拼前再校验”四道规则，见决策 004；`SqlBuilderTest` 覆盖非法输入。
- 建表和改表也要自己写：`DdlBuilder`/`SchemaSync` 和查询 SQL 是两套代码，模型改动时要同时检查；这是动态模型的固有成本。
- 没有 ORM 的关联加载、缓存、懒加载；本项目不需要，BOM 的 `{id,label}` 用一次 `IN` 查询批量取，够用且 SQL 条数固定。
- AI 最初把“MyBatis-Flex 依赖实体类”说得过绝对；组长核对文档后修正为“可以用 Db+Row，但在动态模型场景收益不够”。这提醒我们：AI 的框架比较也要自己查文档，不能直接当结论。

### 2.12.7 AI 在这个问题上的作用

事实部分：骨架是 Claude Code 搭的，一开始就用了 `JdbcTemplate`，所以这个选择是 AI 先做出、组长事后确认的。它最初给的理由不够准确，见上面“需要组长核对的一点”；核对后把绝对化的说法改成了“收益不够”，最终选择由组长确认。

## 2.15 后端启动报 Unable to establish loopback connection

- 负责人：后端（组长）
- 关联任务：搭项目骨架
- 状态：已解决
- 最后更新：2026-11-26

这份记录里的现象、排查过程和结果，是 2026-11-13 搭骨架时在组长电脑上实际发生的，由组长使用 Claude Code 排查并记录。“讨论记录”和“反思”两节留给小组补充。

### 2.15.1 问题

后端骨架的单元测试通过，但真正启动时 Tomcat 起不来，接口无法访问。日志里的关键信息：

```
java.io.IOException: Unable to establish loopback connection
Caused by: java.net.SocketException: Invalid argument: connect
    at java.base/sun.nio.ch.UnixDomainSockets.connect0(Native Method)
    at java.base/sun.nio.ch.PipeImpl$Initializer$LoopbackConnector.run(PipeImpl.java:123)
    at java.base/sun.nio.ch.WEPollSelectorImpl.<init>(WEPollSelectorImpl.java:78)
    at org.apache.tomcat.util.net.NioEndpoint$Poller.<init>(NioEndpoint.java:631)
```

### 2.15.2 排查过程

1. 单元测试为什么没发现：测试用的是 MockMvc，不启动真正的 Tomcat，所以不会走到这段代码。
2. 写了一个只有一行 `Selector.open()` 的 Java 小程序来复现。结果：
   - JDK 24 和 JDK 21 都失败，说明不是某个 JDK 版本的问题。
   - 报错位置在 JDK 内部：Windows 上，JDK 创建 NIO 的 `Selector` 时，会在临时目录里建一个本地套接字（Unix domain socket）文件，再自己连接它。在这台电脑上，建文件成功，连接失败。
3. 用 JDK 的参数 `-Djdk.net.unixdomain.tmpdir` 把套接字文件换到别的目录：
   - 换到 `C:\Windows\Temp`、`C:\Users\Public`、项目的 `backend\target`：都成功。
   - 用系统默认的临时目录（`C:\Users\用户名\AppData\Local\Temp`）：失败，不管写成长路径还是短路径。
4. 结论：问题只和这台电脑的用户临时目录有关，和路径里有没有空格、路径长短无关。根本原因没有继续查。

### 2.15.3 候选方案

| 方案 | 怎么做 | 好处 | 代价 |
|---|---|---|---|
| A | 在文档里写明：遇到这个错误就加 JVM 参数 | 不改代码 | 每种启动方式（命令行、IDEA、jar）都要各自配置，容易漏 |
| B | 在 `pom.xml` 的 Spring Boot 插件里配置 JVM 参数 | 只改构建配置 | 只对 `mvnw spring-boot:run` 有效，IDEA 直接运行和 `java -jar` 不生效 |
| C | 在启动类 `main` 方法的最开头，用代码设置这个系统属性，指向当前工作目录 | 任何启动方式都生效，组员不用做任何配置 | 启动类里多了几行和业务无关的代码 |

: 表 2-32 候选方案


### 2.15.4 结论

选了 C，代码在 `MetaforgeApplication.useWorkingDirForLoopbackSockets()`。几个细节：

- 只在 Windows 上生效。
- 如果启动命令里已经指定了这个参数，不覆盖。
- 当前工作目录不可写或路径太长时，JDK 会自己退回到普通的 TCP 回环连接，所以这样设置不会让原本正常的电脑出问题。

验证：改完后不加任何 JVM 参数，用 `java -jar` 启动，Tomcat 正常启动，健康检查接口返回 `UP`，后端目录里没有残留的套接字文件。

# 4 AI 协作反思

三个人的学习日志里记录了 AI 给出不合适方案、以及我们如何发现和处理的过程，汇总如下。

## 4.1 AI 写的检查不等于检查

组长在 B4 让 AI 写联调预检脚本，脚本只检查页面文字里有没有“模块数/模型数”，没有断言具体数字，因此首页统计全是 0 也没有报错，是看截图时发现的。后来补了“2/4/21”的断言再复测。AI 能跑很多检查，但它写的断言本身也要审。

## 4.2 AI 不熟悉真实环境

B2 的备份表名只精确到秒，同一秒内连续删除两次会重名；单元测试没有发现，在真实 MySQL 上验收才暴露。另外 B3 的验收脚本取查询结果时只截到首字符，报了一个假失败。结论：AI 写的代码和验收脚本都要在真实环境里再跑一遍，H2 通过不等于 MySQL 通过。

## 4.3 AI 会给出不可执行的用例

文档同学让 AI 按功能清单铺测试用例，AI 写出“物料编码填重复值”这种步骤，但物料编码是只读字段，界面上根本输不进去，只能改用编码规则的“规则名称”测唯一校验。AI 给的用例必须对着接口契约逐条核。

## 4.4 AI 会打乱流程顺序

组长让 AI 协助合并叠加的 PR，AI 先删除了下层分支，导致 GitHub 自动关闭了依赖它的 PR。后来按“先改下一个 PR 的 base、再合并、最后删旧分支”的顺序修正。

## 4.5 小结

AI 在代码初稿、批量检查、文档起草上节省了大量时间，但需求理解、验收标准、真实环境验证和流程判断仍由人负责。我们把 AI 的错误当作流程检查点，而不是让它直接产出结论。
