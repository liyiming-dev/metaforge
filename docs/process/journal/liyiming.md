**遇到的问题和解决过程**（现象 → 原因 → 怎么解决的）

思考导入原子性时，原本想让整次导入完全回滚，但 MySQL 的 `CREATE TABLE` / `ALTER TABLE` 执行即隐式提交，数据库本身做不到回滚。最后在 010 里诚实写明边界：新建表失败靠补偿删表，已有表改到一半失败无法自动回退、只能靠导入前备份，并在文档和 PPT 里把这条限制讲透，不假装 100% 原子。

**今天弄懂的一件事**（用自己的话写，假设是讲给没做过这部分的组员听）

`MetaRegistry` 用 `volatile` 指向一个不可变 `Snapshot` 记录，刷新时先从数据库把全部模块和模型读齐、组装成新对象，再一次性替换引用。这样并发请求要么读到完整的旧定义，要么读到完整的新定义，不会读到“模型加了一半”的中间状态。

**遇到的问题和解决过程**（现象 → 原因 → 怎么解决的）

编码规则的 `generate` 如果写成“先查 `current_serial` 再加 1 写回”，并发请求会拿到同一个流水号。改为在 `ScriptDb.increment` 里直接执行原子 `UPDATE ... SET current_serial = current_serial + 1 WHERE id = :id` 拿行锁后再读回，20 线程并发新建物料实测拿到 20 个互不重复的编码。另外给 `db.call` 限制只能调 `manual` 服务并加环检测，防止脚本递归死循环。

**今天弄懂的一件事**（用自己的话写，假设是讲给没做过这部分的组员听）

选脚本引擎最核心的不是谁跑得快，而是**能不能关进沙箱**。Groovy 依赖 7.4 MB、沙箱和死循环限制都要自己额外配；AviatorScript 只有 0.6 MB、内置 sandbox、执行超时和循环上限，再配合只暴露 6 个受控函数的 `ScriptDb`，脚本根本碰不到 `JdbcTemplate` 和底层类。

**遇到的问题和解决过程**（现象 → 原因 → 怎么解决的）

B2 验收时连续删建同一个模型，第二次删除失败。原因是备份表名只精确到秒，同一秒内删两次会重名；改成精确到毫秒后解决，并补了“连续新建、删除三次”的测试。这个问题单元测试没发现，是真实 MySQL 验收暴露的。

B3 的验收脚本自己也出过错：取查询结果第一行时只截到首字符，报了一个假 FAIL；修脚本后重跑才是真结果。验收脚本也要当代码审查。

**今天弄懂的一件事**（用自己的话写，假设是讲给没做过这部分的组员听）

MySQL 的建表改表不能回滚，所以“保存定义”和“改表”的顺序很重要。我们的做法是先校验、再改表、成功后才保存定义；改表失败时定义还是旧的，表和定义至少对得上。删字段不物理删列，而是改名成 `zz_` 开头留备份，误删还能找回数据。
