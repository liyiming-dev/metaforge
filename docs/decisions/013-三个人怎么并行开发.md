# 013 三个人怎么并行开发

- 负责人：全组
- 关联任务：项目骨架
- 状态：已定
- 最后更新：2026-11-26

## 问题

三个人分别负责后端、前端、文档，接口多、时间只有两周多。要决定怎么并行：先等后端做完前端再开始，还是先约定接口各自开发，以及代码怎么合并。

## 候选方案

| 方案 | 怎么做 | 好处 | 代价 |
|---|---|---|---|
| A 先定契约，前端对 mock | 先写 `docs/contract/`，后端按契约实现，前端按契约写 mock，最后切真实后端联调 | 两条线并行；接口问题在契约阶段暴露 | 契约要维护，mock 与后端可能不一致 |
| B 后端做完，前端再开始 | 串行开发 | 接口稳定 | 工期翻倍，前端长时间闲置 |
| C 各自开发，最后合并 | 并行但不约定接口 | 启动快 | 合并冲突和返工多，接口对不上 |

## 试做和测试

实际按 A 执行：

- 11/13 搭骨架时先写接口契约，之后每个功能的接口先改契约、前后端确认再实现。
- 前端 F1–F6 先对着 `frontend/src/mock` 开发，后端 B1–B6 并行实现。
- 每个任务一个分支、一个 PR，组长评审后合并，提交信息用中文。
- 11/23 联调 2 切真实后端，按清单验收 5 项全部通过。

联调中发现过 mock 与后端不一致：mock 的校验比后端松，F5 的“逐字输入把半截字段名写进视图”在 mock 里点不出来，切真实后端才暴露，后来单独修复。这说明 mock 只能加速开发，不能替代联调。

## 结论

选 A。契约是并行开发的前提，mock 让前端不用等后端，分支加 PR 让合并可控。代价是 mock 与真实后端存在差异，必须安排联调；契约变更要同步 mock 和文档。

## 代价和反思

- mock 不是后端：校验松、行为可能不同，联调必不可少。
- 契约每次变更都要同步 mock、前端类型和文档，否则会按旧契约开发。
- 分支加 PR 增加了评审环节，但避免了直接改 main；叠加 PR 的合并顺序要小心，本次就遇到过删下层分支导致上层 PR 被自动关闭的问题。
- 如果重来，会在契约里把错误码和字段级错误格式写得更细，减少联调时的对齐成本。

## AI 在这个问题上的作用

AI 按契约生成 mock、前端组件和后端代码，也协助跑构建和验收；契约内容、验收口径和联调结论由组长和全组确认。AI 不参与“是否并行”的决策。
