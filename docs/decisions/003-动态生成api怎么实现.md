# 003 “动态生成 api”怎么实现

- 负责人：后端（组长）
- 关联任务：B3
- 状态：已定，选方案 A（一个通用控制器）
- 最后更新：2026-11-15

## 问题

课题要求“平台可以动态加载元模型定义信息，动态生成 api”。元模型是运行时在页面上定义的，写代码时不知道会有哪些模型、哪些字段，所以数据接口不能像普通项目那样一个模型写一个 Controller。要决定的是：接口怎么做到“新建一个模型，它的增删改查立刻可用，不用重启”。

## 候选方案

| 方案 | 怎么做 | 好处 | 代价 |
|---|---|---|---|
| A 一个通用控制器 | `DataController` 上写 `@RequestMapping("/api/data/{model}")`，模型名是路径变量。每次请求去内存注册表里查模型定义，再按定义拼 SQL | 实现简单，一个类五个方法；模型删了不用清理任何映射；接口文档只有一份；新建模型后接口立刻能用 | 所有模型的接口在地址上长得一样，只能靠路径区分；没法给单个模型加特殊接口 |
| B 运行时注册映射 | 每新建一个模型，就往 Spring 的 `RequestMappingHandlerMapping` 里注册一组新的映射；删除模型时再摘掉 | 名字上更像“动态生成”：每个模型确实有自己的映射 | 映射表不是给应用层增删设计的：要自己处理注册唯一性、多实例、并发；删模型要保证摘干净，否则留下“模型没了但接口还在”；接口文档、路由排查都变难 |

## 试做和测试

按方案 A 试做。关键实现（`backend/src/main/java/com/metaforge/data/DataController.java`）：

```java
@RestController
@RequestMapping("/api/data/{model}")
public class DataController {
    @PostMapping("/search")          // 分页查询
    @GetMapping("/{id}")             // 详情
    @PostMapping                     // 新建
    @PutMapping("/{id}")             // 修改
    @DeleteMapping("/{id}")          // 删除
}
```

每次请求都从 `MetaRegistry.requireModel(model)` 现取定义。`MetaRegistry` 在元模型保存后整份替换快照，所以：

- 新建一个模型后不重启，`POST /api/data/supplier` 立刻能调（`DataApiTest.newModelIsUsableWithoutRestart`）；
- 模型不存在时五个接口都返回 404（`DataApiTest.unknownModelReturnsNotFound`）。

方案 B 没有实现。理由是：Spring 在启动期就把映射表建好了，运行时增删要自己管生命周期（重复注册、删除时清理、多实例各管各的），换来的只是“路由名字不同”；而验收标准里并没有这一条。

## 结论

2026-11-15 组长确认用方案 A：一个通用控制器，模型名作路径变量。

决定性的理由：课题要求的“动态生成 api”，结果上要的是**接口跟着模型定义走**——新建模型、改字段、删模型，接口的可用性和字段都跟着变，A 已经满足；B 做到的是“路由名字跟着模型走”，只是形式上的动态，代价却是运行期管理 Spring 的映射表，容易留下“模型删了、路由还在”的脏路由。

## 代价和反思

放弃了“每个模型一个独立 URL 路径”这种更直观的形态。代价是：以后如果某个模型需要特殊接口（例如 MES 里的“报工”），要么放在服务接口 `/api/svc` 里，要么给通用控制器加一条更具体的路径（Spring 会优先匹配更具体的写法）。
