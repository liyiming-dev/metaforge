# 009 关联关系怎么表达

- 负责人：后端（组长）、前端
- 关联任务：B4、F4
- 状态：已定
- 最后更新：2026-11-17

## 问题

模型之间会有两种关联：多对一（产品 BOM 里的“物料”指向一条物料）和一对多（产品里的“BOM 明细”是一组产品 BOM）。要决定四件事：

1. 多对一字段在响应里返回什么：只返回 id、返回整条目标记录，还是别的形式。
2. 一对多怎么保存：保存产品时一起保存明细，还是明细单独增删改。
3. 要不要建数据库外键来保证引用完整性。
4. 多对一的显示文字（label）怎么取，才能既不逐条查，也不把 SQL 写得太复杂。

## 候选方案

| 小问题 | 方案 | 做法 | 好处 | 代价 |
|---|---|---|---|---|
| 1 多对一返回什么 | A | 只返回 id | 响应小 | 列表要显示名称时前端得再查，一页 10 条就是 10 次请求 |
| 1 | B | 返回整条目标记录 | 前端什么都有 | 列表只用得着名称，却把所有字段甚至目标记录的关联一起带过来 |
| 1 | **C（选）** | 返回 `{ "id": 3, "label": "螺丝 M3" }` | 一个字段既够显示又够提交，列表不用补查 | 后端要多查一次 label |
| 2 一对多怎么保存 | A | 保存产品时级联保存明细 | 前端一次提交 | 前端要记新增/修改/删除，后端要多表事务，部分失败时整张表单白填 |
| 2 | **B（选）** | 明细单独调子表模型的接口增删改 | 每个接口只做一张表，失败范围小 | 新建产品要先保存，才能加明细 |
| 3 要不要外键 | A | 建数据库外键 | 数据库兜底 | 改表是“改名留备份”，外键会挡着；删被引用记录时数据库只给笼统错误，说不出被谁引用 |
| 3 | **B（选）** | 不建外键，写入查目标存在、删除查引用 | 改表和备份不受外键约束；错误能说清是哪条引用 | 脏数据要靠程序兜住，应用层多两次查询 |
| 4 label 怎么取 | A | 每条记录查一次目标表 | 实现简单 | 一页 N 条就是 N 次查询 |
| 4 | B | JOIN 目标表 | 一条 SQL | 表名列名运行时拼，JOIN 要处理重名和关联不存在；一个 JOIN 只能带一个显示字段 |
| 4 | **C（选）** | 收集这一页同一关联字段的 id，一条 `WHERE id IN (...)` 取回，再拼 `{id,label}` | 查询条数只跟关联字段数有关，跟记录数无关 | 每个关联字段多一条查询 |

## 结论

2026-11-16 晚确认，四条都按建议方案：

1. 多对一在响应里返回 `{ "id": 3, "label": "螺丝 M3" }`，请求里传 id；后端也兼容把读到的 `{id,label}` 原样传回来，只取 id。
2. 一对多不级联保存，子表记录单独调接口增删改；新建产品先保存，再添加明细。
3. 不建数据库外键；B4 在写入时检查关联目标存在，在删除时检查有没有别处引用，有就返回 409 并说明被哪个模型引用。
4. label 用“收集一页的 id → 一条 `IN` 查询”批量取；查询条数只跟这一页有几个关联字段有关，跟记录数无关。

决定性的理由：这四条让前端只面对普通 JSON，不需要知道关联表怎么拼；后端又把查询次数控制在一页固定几条，不随数据量增长。代价是新建产品多一步保存，以及脏数据要靠程序检查兜住。

## 代价和反思

- 不级联保存，用户必须先保存产品才能加 BOM 明细。F4 用“先保存，再添加明细”的提示把这一步说明白了。
- 不建外键，数据库不会兜底。B4 写入和删除各加一次检查；如果以后直接改数据库，仍可能产生脏数据。
- 批量 `IN` 比逐条查好，但每个关联字段仍要多一条查询；产品 BOM 有产品、物料两个关联，一页固定 4 条查询（2 条基础 + 2 条 label）。
- 如果重来，可能把 `displayField` 在模型保存时就校验成“必须是目标模型的 string 字段”，而不是等到第一次读数据才报错。

## AI 在这个问题上的作用

AI 先把“只返回 id / 返回整条记录 / 返回 `{id,label}`”和“逐条查 / JOIN / 批量 IN”的代价列出来，建议选 `{id,label}` + 批量 IN；组长按这个方向发到群里，前端确认同意。AI 没有替组长做决定，四条都是组长确认、前端同意后才定下来的。
